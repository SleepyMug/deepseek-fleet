# TODOs

- **Spill files.** Oversized results keep only what fits: bash output keeps its tail and reports the full output as unavailable, spill-policy is disabled, so large tool results stay inline, and spill-local is disabled, so a reference to another session says its full transcript is unavailable. All of them spill to host files the model cannot open from its container. The helper could write spills inside the container instead and report their container paths, so both `cat` and `read` find them.
- **Local images need the session.** session-controller's `/api/file`, which shows images of local paths in the chat and in a Markdown preview, is refused: its requests name no session, and fleet-box serves a path that names no container only to a session's own work. dsh's client would have to send the session with the request, and the handler read the file on that session's behalf.
- **Watching in the container.** The helper has no watches, so the file viewer and the file tree do not refresh on their own; dsh's change feed reports watching as unsupported. The helper could watch with dsh's local file system and report changes as events. A watch should not occupy its container: the feed holds one for every open folder and preview, so an idle browser tab would keep the container running for good; a watch could instead end with an error the client retries once the container stops. The feed's target names its container, so fleet-box can serve the watch from the target alone, whatever context the feed calls from.
- **Container paths name containers for anyone.** Outside a session's work, fleet-box serves any call whose path or target names a container, read-only, so any code that holds a target or writes `fleet-box://<session>/…` reads that session's container, and starts it if it is stopped. Only workspace-files names containers today, from the lookup fleet-box configures, and a path naming another container than its `cwd` is refused, so a link the model writes cannot reach another session. Should a plugin that passes stored or model-supplied targets to `ctx.fs` outside a turn be enabled, the name could become a capability: a signed root segment that fleet-box mints and checks, with a key that survives a restart if targets are kept across one.
- **Relying on workspace-files.** fleet-box's `workspaceFileScope` lookup gives a session's folder as `fleet-box://<root><cwd>`, which is no host path. It works because dsh's workspace-files passes `workspaceRoot` on to `ctx.fs` untouched, as a path or a `cwd`; should it check, join or show the value, the sidebar fails, refused rather than served from the host. office-to-pdf takes the same lookup but resolves its own plain path with no `cwd`, which fleet-box refuses, so it stays disabled. A test running dsh's real `WorkspaceFiles` over fleet-box's file system would catch a change; dsh passing the session along with the scope would end the reliance.
- **Stream cancellation.** A text stream whose signal aborts between chunks ends as if read to its end, so a consumer can take part of a file for all of it; after an abort, `next()` should fail with `FS_ABORTED`. A stream whose open is cancelled after the helper opened it is aborted there but stays in the helper's table until the container stops; the host could choose stream ids itself, or close a stream whose open it gave up on.
- **Attachments in the container.** Uploaded files stay in dsh's attachment store on the host, which no container mounts, so the model is told an upload has no readable path. They could be copied into the session's container.
- **Image updates keep containers.** fleet's runtime, the helper and the TypeScript runner, is built into the session image, so every `fleet setup image` after a change to either, even a comment, gives a new image id, and once dsh restarts, every session's container is recreated on its next use, losing installed packages and `/tmp`. A container could keep the image it was made from for as long as its labels show the protocols the host speaks, so only a protocol change recreates it. The next use can be the file viewer's, so opening an old session's files after an update recreates its container without any turn; calls outside a session's work could use the stale container, or be refused, and leave the recreation to the next turn.
- **Forks and containers.** A fork gets a fresh container and a notice that earlier installs are gone; it could instead start from a copy of its source's container (`docker commit`), so installed tools carry over.
- **Fleet as one installable product.** Today each piece is added to its profile by hand (`dsh plugin --profile fleet add` for fleet-core, and `dsh plugin --profile fleet-signin add` for fleet-signin), and the `fleet` command, `fleet setup image` included, reaches PATH only by a global link (`pnpm add -g link:<repo>/packages/fleet-client`); a project dependency cannot serve it, since `pnpm exec` finds it only inside that project and `pnpm -C` moves the working directory the session would mount. A top-level `fleet` package, installed globally, could bring dsh and those packages with the `fleet` command, and add starting the host to its subcommands, so setting up a machine is one install beside the image and sign-in steps. fleet-client, which holds the command, loads no dsh module, but it installs fleet-image for `fleet setup image`, which brings the dsh libraries the helper serves files with (dsh-fs, dsh-fs-local and their peers); a CLI-only install could leave them out if `setup` found the image package some other way. Today fleet installs only by linking this checkout, and nothing documents the steps: every package is private.
- **dsh version pins.** Every package pins dsh 0.1.7-rc.2 exactly, in four manifests, so fleet runs on that release only; the root's `@deepseek-ai/dsh` devDependency pulls in all of dsh, which is why `minimumReleaseAgeExclude` lists so many packages. The version could live in one place, and become a range once dsh's releases allow it.
- **Rootful Docker.** Workspace files stay the user's only under rootless Docker, where the container's root is the host user; under rootful Docker, the default of most Linux installs, files the model writes in the workspace become root's. Nothing checks: `fleet setup image` or startup could read `docker info`'s security options and warn, or the container could run as the host user.
- **Other Docker setups.** The bind mount at the same path needs a Docker daemon that sees the host's files, so a remote `DOCKER_HOST` or context does not work, and a workspace under `/opt/fleet`, `/tau` or another of the container's own paths hides it; neither is checked. `fleet setup image` always runs `docker`, whatever fleet-box's `docker` setting, and it copies fleet-image with the packages it depends on as installed on this machine, whose package manager chose the platform-specific ones (koffi's and esbuild's binaries), so it builds only on Linux with the Docker daemon's architecture. The world checks a folder with the host's `isAbsolute` but serves files with POSIX paths, so a Windows host fails obscurely. Containers carry the dsh home's path in a label, so moving `DSH_HOME` orphans them and recreates every session's container, and a deeply nested `DSH_HOME` can push the control socket past the Unix socket path limit.
- **This machine's setup.** Messages assume `dsh` on PATH and profiles named `fleet` (`dsh --profile fleet` in the `fleet` command's help) and `fleet-signin` (`dsh fleet-signin` in fleet-signin's). A profile's model setup, its default model and their context windows, is its own cordis.patch.yml, which nothing writes for a new profile.
- **More of the subprocess seam.** The container world serves what bash needs, collected output and stdin ignored or given as data, and the sidebar's terminals. Raw pipes and the fd 7 control channel (PTC) are refused, so fs-search, LSP and PTC stay off; they would need per-stream flow control between host and helper.
- **Background jobs.** The fleet preset runs bash in the foreground only (`enableRunInBackground: false`, `promoteOnTimeout: false`, no `tool-jobs`), so a command past its timeout is killed, and what a command leaves running with `&` does not keep its container, so it ends when the container idles out. With background jobs an idle agent is not a finished one: a job outlives the turn that started it, and its completion wakes the agent with another turn. Jobs would have to occupy their container (fleet-box's occupancy) from before they start until their processes are gone, or it stops under them; `fleet run`/`wait` would have to wait until no job or subagent runs either and report every turn since; and Ctrl-C would have to stop the session's jobs as well as its turn, or an interrupted run leaves work, and its container, running.
- **Releasing agents.** The session controller creates an agent for every session it runs, and nothing releases one: the web app never does, and fleet-control holds no handle, since only the creator can dispose an agent. Each `fleet run` leaves its agent, log and writer lock in the host until dsh exits, which scripted runs make unbounded. Releasing an idle agent needs a way through dsh's session controller.
- **Waits that survive a host restart.** A plugin reload or host restart closes the control socket's connections, so a waiting `fleet run`/`wait` exits 1 while its session keeps running and its container is not stopped. The command knows the session by then and could reconnect with a backoff and wait again.
- **Wait deadlines.** `fleet run` and `fleet wait` wait for as long as the session runs; a `--timeout` could cancel the turn after a while, or return while leaving it running.
- **Cheaper outcomes.** `wait` reads the session's whole log through `sessionController.inspect` to find the outcome, parsing it from disk for a session no agent holds; a live agent's session could be read by sequence number instead, as dsh's headless runner does.
- **Tests for the control path.** fleet-client's, fleet-protocol's and fleet-control's tests cover the agent's variables, framing and outcomes; the socket server (claiming, one request per connection, abort on close) and the control operations against a fake session controller have none, and neither has fleet-box's world beyond its occupancy and its file system's routing against a stub world: closing (a turn or terminal starting around a close, the idle stop, `stopSession` for a subagent id), and terminals and file calls against a real container. fleet-tau's tests stand in fakes for fleet-box, so its publish test copies with a fake; its agent plugin is tested only for failures, never for registering skills and tools or releasing their scopes, and its TypeScript tools are not tested at all. Nor are a tau run's subagent provider and backend, beyond the symlinks they refuse: the smoke test reads, stores and publishes such a run through real containers, but no subagent runs it, which takes a model; fleet-box's container owners, a subagent's own container included, are tested only through its file system's stub world.
- **One lineage walk.** The world walks a session's lineage twice: `ownerHeader` over loaded sessions only, `ownerHeaderOf` over loaded or stored ones, and `archivedLineage` a third time for archives. So `ctx.subprocess` refuses a subagent whose parent is not loaded while `ctx.fs` serves it, and `stopSession` takes a stored subagent's id for an owner and reports it stopped. One walk over a pluggable lookup, with `ownerHeaderOf` taking a header, would align them, and the file viewer's lookup would read the session's header once. Smaller duplicates: `abortable`, `message` and `MAX_TIMER_DELAY_MS` in several modules, and the terminate margin and probe interval in both subprocess.ts and terminal.ts. fleet-tau and fleet-control have a `message` and an `abortable` of their own too, and some rules are kept twice: the session id pattern, in fleet-tau's store and fleet-box's world, and the checks that keep paths out of the container's reserved folders (fleet-image/layout's), in fleet-box's additions and fleet-tau's paths.
- **Error codes and messages.** Outside a session's work, a call naming an unknown or archived session fails with `FS_IO_ERROR` rather than `FS_PERMISSION_DENIED`, since the world's errors pass through as I/O failures, and the file viewer's lookup still answers for an archived session, and fails rather than resolving nothing for a subagent whose parent is gone. fs.ts's messages carry no `fleet-box:` prefix, unlike the world's, and its `FS_ERROR_CODES` is copied from dsh-fs by hand, so a code dsh adds arrives as `FS_IO_ERROR`.
- **Terminal ownership and idleness.** A sidebar terminal's processes are those in the container that carry its marker variable, share its shell's session, or descend from one of them while it lives, so one that hides the marker, starts a session of its own and outlives its parent between two of the helper's lookups, as a quickly daemonizing server run as another user can, is not the terminal's: closing the terminal does not end it, and it runs until it ends or the container stops. A terminal counts as idle, which lets the terminal controller reclaim it once nobody has it open, when its shell is its only process, holds the foreground and sleeps; a loop of shell builtins that sleeps looks the same. Prompt markers from the shell, as dsh's local provider injects, would tell for sure. Container process groups mean nothing on the host, so a terminal's foreground group is neither reported nor signalled, which dsh's model-facing terminal tool would need. The Docker CLI's detach keys cannot be turned off, so a lone `Ctrl-\` reaches the shell only with the next key.
- **Paths and the workspace dir.** Path arguments may overlap each other and the workspace dir, which the container mounts as the agent's working folder, so the agent sees, and can change, the caller's own files there beside an `in` path's snapshot or an `out` path's folder under /tau; tau's SPEC.md promises nothing about what one path shows of another. Publishing an `out` folder over a folder renames its entries in one by one, so a reader can see old and new files mixed while it runs, and it keeps only the folders the agent left as folders: an `out` path that holds the workspace dir or a `share` path, where the agent left no folder, removes a folder a container mounts, and the container then cannot start until the folder exists again. `fleet check` no longer takes `--cwd`, and its request no longer carries the workspace dir, without a new protocol version, so an older host refuses this client's `fleet check`.
- **Outputs, when and how.** An `out` path is published after a completed turn that a `fleet run` or `wait` waited on, so an `--async` run publishes at `fleet wait`, and a turn a person steered in the web UI publishes nothing until a command waits. The copy goes through the helper in 4 MiB chunks of base64, which is slow for large outputs, and starts a stopped container, and so does copying the agent's snapshot or an `in` path into a container; the helper is used because rootless Docker's `docker cp` fails for a container with a read-only bind mount from a filesystem mounted nosuid, nodev or noexec, whatever path it copies. fleet-tau now asks for no read-only mount, so `docker cp` may serve instead. A copy is bounded in bytes, not in files or depth, so an output of many small files makes as many on the host.
- **Paths and variables of a run.** A `share` file is mounted as the file itself, so a program that replaces it by renaming another file over it, as publishing an `out` path at the same file does, leaves the container with the old one. An `in` path is copied whole when the session is made, however large, and, as the agent's snapshot is, again into each container the session gets, which delays the container's first use; the caller's later changes to it never reach the session, while the agent's changes to its copies, its own skills and API files included, last as long as the container. The helper protocol gained the copy-in requests without a new version, so a helper from an older image refuses them, and with them every session `fleet run` starts. The caller's values of the variables tau.json lists are kept in the spec and passed with `docker run --env`, so `docker inspect` shows them. A fork gets its source's `in` snapshots, but neither its other paths nor its variables, apart from what of them lies in the workspace dir, which it shares with its source.
- **Stored state of a session.** Nothing removes a session's folder in the store: its snapshot, the whole agent directory, however large, since its APIs may import any file in it, the snapshots of its `in` paths, and its spec with the caller's variables. Nor is a session's container additions file removed once the session is gone. A root session's additions are written once, when it is made, so a change to what fleet-tau adds reaches only new sessions, while a fork's are written again each time its agent starts. Sessions made before fleet-tau moved to /tau still have the agent copied to /opt/fleet-tau/agent, where its skills and APIs are no longer looked for, and their specs, if they have path arguments, are refused as not valid rather than as older ones, since the spec's version has not changed.
- **TypeScript runs cut short.** A runner killed after its grace leaves ts-executor's folders for that run in /tau/ts/.ts-executor.
- **Runs inside a container.** A tau started from inside a session's container, through the `tau` API or command, runs as a one-shot dsh subagent of the caller, which fleet-tau's own subagent provider starts; the provider finds the run the backend read by the prompt array dsh's subagent service passes on to it as it is, which nothing in dsh promises. The run's container is kept, stopped, until the caller's session, or one it lies under, is archived, so a caller that runs many keeps many containers, and their store folders. The caller's agent must be loaded here, so a terminal of a session no agent holds cannot start one. Its agent directory, copied out of the caller's container, is read on the host by tau's library, which type-checks API declarations the model may have written; its symlinks are checked to stay inside it first, but TypeScript still resolves what those declarations import. There is no ahead-of-time check from inside a container, as `fleet check` is from outside. A run left in `$DSH_HOME/fleet/staging` by a host that died while copying is never removed.
- **Backends and subagents.** A backend call names no session; fleet-box relays it for the session whose container it came from: a tau run's own, or for any other subagent, the parent's whose container it uses, so such a subagent's calls reach backends as its parent's. Nothing in the fleet preset starts other subagents today.
- **Limits.** For now nothing bounds how long a run, a program or a backend call takes: `ts_execute` runs a program until it returns or its call is cancelled, backend calls have no default timeout, and a container may have any number of calls in flight, so a program can wait on as many tau runs as it starts. Nor is a tau run's depth bounded: a tau that runs itself recurses, a container per level. The `tau` command, though, runs under bash's timeout, a minute in this profile unless the call raises it, up to bash-local's cap of ten minutes, so a long run is started from a program instead. What a tau run copies out of its caller's container, its agent directory and its `in` paths, has no byte limit, while the outputs it gives back keep theirs, as do the publish timeout and the like. Limits are to be designed together, as one scheme.
- **Versions after recursive runs.** The helper protocol gained `copyOut.readlink`, `copyOut.mode` and `copyIn.replace`, the runner's requests lost their required `timeoutMs`, a spec may name its `caller`, and the control protocol lost `send`, all without new versions: an image built before needs `pnpm image` for nested runs and for `ts_execute`, an older host would read a nested run's spec as a run from the host, and this host refuses an older client's `fleet send` as a request it does not know.
- **Implementations in step with the image.** fleet checks an agent's APIs against fleet-image's implementations as installed on the host, while containers run the copy the session image was built with, and nothing checks that the two match: changing an implementation without `pnpm image` runs agents on the old one, which may no longer fit their APIs. A label with a digest of the package, checked as the runner's protocol is, would catch it.
- **Sibling checkouts.** tau, ts-executor and pi-run are members of this workspace from checkouts of their own in `../agent_fleet_project`, which must be there: `pnpm build` builds them before fleet, and this lockfile pins their dependencies, which `fleet setup image` copies with ts-executor. A `pnpm install` inside one of them installs it on its own again, from its own lockfile, until the next install here, and their own pnpm settings do not apply here. fyona, a workspace of its own, still resolves ts-executor through a `file:` override. Once tau and ts-executor are published, fleet can depend on releases instead. fleet-tau also depends on TypeScript at runtime, to compare service manifests.
- **A fork's first container.** A fork of a session started from an agent directory takes its source's snapshot as a container addition, which fleet-tau sets when the fork's agent is announced, before its first step. If the file viewer opens the fork's files before that, the container is made without the snapshot and recreated at the first step, losing anything installed in between.
