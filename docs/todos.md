# TODOs

- **Spill files.** Oversized results keep only what fits: bash output keeps its tail and reports the full output as unavailable, spill-policy is disabled, so large tool results stay inline, and spill-local is disabled, so a reference to another session says its full transcript is unavailable. All of them spill to host files the model cannot open from its container. The helper could write spills inside the container instead and report their container paths, so both `cat` and `read` find them.
- **Local images need the session.** session-controller's `/api/file`, which shows images of local paths in the chat and in a Markdown preview, is refused: its requests name no session, and fleet-box serves a path that names no container only to a session's own work. dsh's client would have to send the session with the request, and the handler read the file on that session's behalf.
- **Watching in the container.** The helper has no watches, so the file viewer and the file tree do not refresh on their own; dsh's change feed reports watching as unsupported. The helper could watch with dsh's local file system and report changes as events. A watch should not occupy its container: the feed holds one for every open folder and preview, so an idle browser tab would keep the container running for good; a watch could instead end with an error the client retries once the container stops. The feed's target names its container, so fleet-box can serve the watch from the target alone, whatever context the feed calls from.
- **Container paths name containers for anyone.** Outside a session's work, fleet-box serves any call whose path or target names a container, read-only, so any code that holds a target or writes `fleet-box://<session>/…` reads that session's container, and starts it if it is stopped. Only workspace-files names containers today, from the lookup fleet-box configures, and a path naming another container than its `cwd` is refused, so a link the model writes cannot reach another session. Should a plugin that passes stored or model-supplied targets to `ctx.fs` outside a turn be enabled, the name could become a capability: a signed root segment that fleet-box mints and checks, with a key that survives a restart if targets are kept across one.
- **Relying on workspace-files.** fleet-box's `workspaceFileScope` lookup gives a session's folder as `fleet-box://<root><cwd>`, which is no host path. It works because dsh's workspace-files passes `workspaceRoot` on to `ctx.fs` untouched, as a path or a `cwd`; should it check, join or show the value, the sidebar fails, refused rather than served from the host. office-to-pdf takes the same lookup but resolves its own plain path with no `cwd`, which fleet-box refuses, so it stays disabled. A test running dsh's real `WorkspaceFiles` over fleet-box's file system would catch a change; dsh passing the session along with the scope would end the reliance.
- **Stream cancellation.** A text stream whose signal aborts between chunks ends as if read to its end, so a consumer can take part of a file for all of it; after an abort, `next()` should fail with `FS_ABORTED`. A stream whose open is cancelled after the helper opened it is aborted there but stays in the helper's table until the container stops; the host could choose stream ids itself, or close a stream whose open it gave up on.
- **Attachments in the container.** Uploaded files stay in dsh's attachment store on the host, which no container mounts, so the model is told an upload has no readable path. They could be copied into the session's container.
- **Helper updates keep containers.** The helper is built into the session image, so any change to its sources, even a comment, gives a new image tag, and every session's container is recreated on its next use, losing installed packages and `/tmp`. The helper could live outside the image instead, mounted read-only at a fixed path and reporting its version in `hello`, so an update restarts only the helpers. The next use can be the file viewer's, so opening an old session's files after an update recreates its container without any turn; calls outside a session's work could use the stale container, or be refused, and leave the recreation to the next turn.
- **Forks and containers.** A fork gets a fresh container and a notice that earlier installs are gone; it could instead start from a copy of its source's container (`docker commit`), so installed tools carry over.
- **Fleet as one installable product.** Today each piece is added to the fleet profile by hand (`dsh plugin --profile fleet add` for profile-fleet, fleet-box, fleet-tau, fleet-control and fleet-setup), and the `fleet` command reaches PATH only by a global link (`pnpm add -g link:<repo>/fleet-control`); a project dependency cannot serve it, since `pnpm exec` finds it only inside that project and `pnpm -C` moves the working directory the session would mount. A top-level `fleet` package, installed globally, could own the `fleet` command and bring dsh and those packages with it, with setup and starting the host as its subcommands, so setting up a machine is one command beside the image and sign-in parts. A CLI-only install then should not pull in fleet-control's plugin peers, which it never loads. Today fleet installs only by linking this checkout, and nothing documents the steps: every package is private, fleet-setup depends on all of fleet-box as `workspace:*` at runtime, node-pty and dsh peers included, though it uses only `fleet-box/image`, and fleet-control uses fleet-box without declaring it as a peer.
- **dsh version pins.** Every package pins dsh 0.1.7-rc.2 exactly, in about eight manifests and the helper's shrinkwrap, so fleet runs on that release only; the root's `@deepseek-ai/dsh` devDependency pulls in all of dsh, which is why `minimumReleaseAgeExclude` lists so many packages. The version could live in one place, and become a range once dsh's releases allow it.
- **Rootful Docker.** Workspace files stay the user's only under rootless Docker, where the container's root is the host user; under rootful Docker, the default of most Linux installs, files the model writes in the workspace become root's. Nothing checks: fleet-setup or startup could read `docker info`'s security options and warn, or the container could run as the host user.
- **Other Docker setups.** The bind mount at the same path needs a Docker daemon that sees the host's files, so a remote `DOCKER_HOST` or context does not work, and a workspace under `/opt/fleet-box` or another path of the image hides it; neither is checked. `fleet-setup image` always runs `docker`, whatever fleet-box's `docker` setting. The world checks a folder with the host's `isAbsolute` but serves files with POSIX paths, so a Windows host fails obscurely. Containers carry the dsh home's path in a label, so moving `DSH_HOME` orphans them and recreates every session's container, and a deeply nested `DSH_HOME` can push the control socket past the Unix socket path limit.
- **This machine's setup.** Messages assume `dsh` on PATH and a profile named `fleet` (`dsh --profile fleet` in fleet-control's and fleet-setup's help), where world.ts already writes `<profile>`, and profile-fleet carries one account's model setup, its models and their context windows, which another user has to patch.
- **More of the subprocess seam.** The container world serves what bash needs, collected output and stdin ignored or given as data, and the sidebar's terminals. Raw pipes and the fd 7 control channel (PTC) are refused, so fs-search, LSP and PTC stay off; they would need per-stream flow control between host and helper.
- **Background jobs.** The fleet preset runs bash in the foreground only (`enableRunInBackground: false`, `promoteOnTimeout: false`, no `tool-jobs`), so a command past its timeout is killed, and what a command leaves running with `&` does not keep its container, so it ends when the container idles out. With background jobs an idle agent is not a finished one: a job outlives the turn that started it, and its completion wakes the agent with another turn. Jobs would have to occupy their container (fleet-box's occupancy) from before they start until their processes are gone, or it stops under them; `fleet run`/`send`/`wait` would have to wait until no job or subagent runs either and report every turn since; and Ctrl-C would have to stop the session's jobs as well as its turn, or an interrupted run leaves work, and its container, running.
- **Releasing agents.** The session controller creates an agent for every session it runs, and nothing releases one: the web app never does, and fleet-control holds no handle, since only the creator can dispose an agent. Each `fleet run` leaves its agent, log and writer lock in the host until dsh exits, which scripted runs make unbounded. Releasing an idle agent needs a way through dsh's session controller.
- **Waits that survive a host restart.** A plugin reload or host restart closes the control socket's connections, so a waiting `fleet run`/`send`/`wait` exits 1 while its session keeps running and its container is not stopped. The command knows the session by then and could reconnect with a backoff and wait again.
- **Wait deadlines.** `fleet run` and `fleet wait` wait for as long as the session runs; a `--timeout` could cancel the turn after a while, or return while leaving it running.
- **Cheaper outcomes.** `send` and `wait` read the session's whole log through `sessionController.inspect` to find the outcome, parsing it from disk for a session no agent holds; a live agent's session could be read by sequence number instead, as dsh's headless runner does.
- **Tests for the control path.** fleet-control's tests cover templates, framing and outcomes; the socket server (claiming, one request per connection, abort on close) and the control operations against a fake session controller have none, and neither has fleet-box's world beyond its occupancy and its file system's routing against a stub world: closing (a turn or terminal starting around a close, the idle stop, `stopSession` for a subagent id), and terminals and file calls against a real container.
- **One lineage walk.** The world walks a session's lineage twice: `rootHeader` over loaded sessions only, `rootHeaderOf` over loaded or stored ones. So `ctx.subprocess` refuses a subagent whose parent is not loaded while `ctx.fs` serves it, and `stopSession`, and with it `fleet stop`, takes a stored subagent's id for a root and reports it stopped. One walk over a pluggable lookup, with `rootHeaderOf` taking a header, would align them, and the file viewer's lookup would read the session's header once. Smaller duplicates: `abortable`, `message` and `MAX_TIMER_DELAY_MS` in several modules, the terminate margin and probe interval in both subprocess.ts and terminal.ts, and image.ts's `PACKAGE_DIR` and `imageInputs`, exported but used nowhere else.
- **Error codes and messages.** Outside a session's work, a call naming an unknown or archived session fails with `FS_IO_ERROR` rather than `FS_PERMISSION_DENIED`, since the world's errors pass through as I/O failures, and the file viewer's lookup still answers for an archived session, and fails rather than resolving nothing for a subagent whose parent is gone. fs.ts's messages carry no `fleet-box:` prefix, unlike the world's, and its `FS_ERROR_CODES` is copied from dsh-fs by hand, so a code dsh adds arrives as `FS_IO_ERROR`.
- **Terminal ownership and idleness.** A sidebar terminal's processes are those in the container that carry its marker variable, share its shell's session, or descend from one of them while it lives, so one that hides the marker, starts a session of its own and outlives its parent between two of the helper's lookups, as a quickly daemonizing server run as another user can, is not the terminal's: closing the terminal does not end it, and it runs until it ends or the container stops. A terminal counts as idle, which lets the terminal controller reclaim it once nobody has it open, when its shell is its only process, holds the foreground and sleeps; a loop of shell builtins that sleeps looks the same. Prompt markers from the shell, as dsh's local provider injects, would tell for sure. Container process groups mean nothing on the host, so a terminal's foreground group is neither reported nor signalled, which dsh's model-facing terminal tool would need. The Docker CLI's detach keys cannot be turned off, so a lone `Ctrl-\` reaches the shell only with the next key.
- **Agent directories, in part.** `fleet run` refuses an agent directory whose tau.json declares path arguments or environment variables, since the container has no way to receive them yet, and one with modules, which nothing gives its programs yet. The tau spec's modes (mount-ro, mount-rw, copy-in, copy-out) map onto the container additions fleet-box already keeps, with the session folder counted as an implicit mount-rw, so a declared path that is, holds or lies in it would be refused.
- **Services and subagents.** A service call names no session; fleet-box relays it for the root session whose container it came from, so a subagent's calls, which run in its root's container, reach providers as the root's. Nothing in the fleet preset starts subagents today.
- **Provider manifests on the host's thread.** `ctx.fleetServices.provide` reads a provider's manifest with tau's library in the host's own thread, loading TypeScript with the first provider, about half a second at startup; agent directories are read in fleet-tau's worker instead. Providers could hand the worker their manifests too, if validating calls moved there.
- **Linked tau.** fleet-tau depends on `@sleepymug/tau` as `link:../../agent_fleet_project/tau`, a checkout that must sit beside this one and be built first; it becomes an ordinary dependency once the package is published. fleet-tau also depends on TypeScript at runtime, to compare service manifests.
- **A fork's first container.** A fork of a session started from an agent directory takes its source's snapshot as a container addition, which fleet-tau sets when the fork's agent is announced, before its first step. If the file viewer opens the fork's files before that, the container is made without the snapshot and recreated at the first step, losing anything installed in between.
