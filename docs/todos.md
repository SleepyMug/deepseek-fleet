# TODOs

- **Spill files.** Oversized results keep only what fits: bash output keeps its tail and reports the full output as unavailable, and spill-policy is disabled, so large tool results stay inline. Both spill to host files the model cannot open from its container. The helper could write spills inside the container instead and report their container paths, so both `cat` and `read` find them.
- **Chat file links.** session-controller serves `/api/file`, the chat's images and file links, through `ctx.fs` outside any session, so the world refuses them. Serving them needs the request's session, to read from its container.
- **Stop idle containers.** `fleet run`, `send` and `wait` stop a session's container when they finish waiting (`FleetBox.stopSession`), but a session opened from the web UI keeps its container, and its helper process, until dsh exits or the session is archived, since the web app never releases a session once it is opened. Close a session's world after a stretch with nothing running, with the same running-work check `stopSession` uses; its teardown stops the container, and the next step starts it again. Processes the model left running in the container die with it.
- **Helper updates keep containers.** The helper is built into the session image, so any change to its sources, even a comment, gives a new image tag, and every session's container is recreated on its next use, losing installed packages and `/tmp`. The helper could live outside the image instead, mounted read-only at a fixed path and reporting its version in `hello`, so an update restarts only the helpers.
- **Forks and containers.** A fork gets a fresh container and a notice that earlier installs are gone; it could instead start from a copy of its source's container (`docker commit`), so installed tools carry over.
- **Fleet as one installable product.** Today each piece is added to the fleet profile by hand (`dsh plugin --profile fleet add` for profile-fleet, fleet-box, fleet-control and fleet-setup), and the `fleet` command reaches PATH only by a global link (`pnpm add -g link:<repo>/fleet-control`); a project dependency cannot serve it, since `pnpm exec` finds it only inside that project and `pnpm -C` moves the working directory the session would mount. A top-level `fleet` package, installed globally, could own the `fleet` command and bring dsh and those packages with it, with setup and starting the host as its subcommands, so setting up a machine is one command beside the image and sign-in parts. A CLI-only install then should not pull in fleet-control's plugin peers, which it never loads.
- **More of the subprocess seam.** The container world serves what bash needs: collected output, and stdin ignored or given as data. Raw pipes, the fd 7 control channel (PTC) and terminals are refused, so fs-search, LSP, PTC and the sidebar terminal stay off; they would need per-stream flow control between host and helper.
- **Background jobs.** The fleet preset runs bash in the foreground only (`enableRunInBackground: false`, `promoteOnTimeout: false`, no `tool-jobs`), so a command past its timeout is killed. With background jobs an idle agent is not a finished one: a job outlives the turn that started it, and its completion wakes the agent with another turn. `fleet run`/`send`/`wait` would then have to wait until no job or subagent runs either (the activity `stopSession` asks about) and report every turn since, `stopSession` would refuse while a job runs, and Ctrl-C would have to stop the session's jobs as well as its turn, or an interrupted run leaves work, and its container, running.
- **Releasing agents.** The session controller creates an agent for every session it runs, and nothing releases one: the web app never does, and fleet-control holds no handle, since only the creator can dispose an agent. Each `fleet run` leaves its agent, log and writer lock in the host until dsh exits, which scripted runs make unbounded. Releasing an idle agent needs a way through dsh's session controller.
- **Waits that survive a host restart.** A plugin reload or host restart closes the control socket's connections, so a waiting `fleet run`/`send`/`wait` exits 1 while its session keeps running and its container is not stopped. The command knows the session by then and could reconnect with a backoff and wait again.
- **Wait deadlines.** `fleet run` and `fleet wait` wait for as long as the session runs; a `--timeout` could cancel the turn after a while, or return while leaving it running.
- **Cheaper outcomes.** `send` and `wait` read the session's whole log through `sessionController.inspect` to find the outcome, parsing it from disk for a session no agent holds; a live agent's session could be read by sequence number instead, as dsh's headless runner does.
- **Tests for the control path.** fleet-control's tests cover templates, framing and outcomes; the socket server (claiming, one request per connection, abort on close), the control operations against a fake session controller, and `stopSession` (a turn starting during its activity check, a subagent id) have none.
